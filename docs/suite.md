## Start Center

Modeled on LibreOffice's Start Center, drawn in the suite's look (see Looks). No title bar of its own (installed, the window has the system's). Left: Open File…, Recent Files, Create File, *Apps*: Quire (word processor), Ledger (spreadsheet), Lectern (presentations), each opening with its demo file, Update VibeOffice (desktop app, when `updater/current.json` asks; docs/desktop.md, Versions and updates) or Check for updates (a version two months old or more, with its age in months, on the site, in the installed PWA and in the desktop app, the Mac App Store edition too: it opens the updater page), Install (on https://vibeoffice.work and 127.0.0.1, when the browser offers it; anywhere else the browser's own prompt is cancelled, `VO.offersInstall`), Feedback on our GitHub, the privacy note and the version, then a row of three links with icons: Settings, Themes (a dialog with a live preview of each look, see Looks) and About. In a narrow window (or a large UI size) the note goes but the links stay. Right, one of two views:

- **Recent Files** (the default): cards (thumbnail, name, app, when), each with a remove button; *Clear Recent Documents*; when the list is empty, the welcome: what the suite is, the three apps with what they do and their formats, why it is different (files kept whole, private, familiar, offline and installable, in your language: the line on offline and installing is hidden in the desktop app), the UI's languages, each in its own name (`translate="no"`), and the drop hint. It is static HTML, so search engines read it (Search engines, below).
- **Create File** (`#create`, so Back returns to Recent Files): Documents, Spreadsheets and Presentations, each starting with Blank (`<app>/?new`) followed by the app's templates (`<app>/?template=<id>`), with a preview of each.

**Settings** (what applies to every app): UI size (the desktop app's zoom, 100–400 %; on the web, a pointer to the browser's own zoom: CSS zoom breaks the apps' hit-testing), Fonts on this computer (load, reload or forget the list Local Font Access gave, where the browser has it) and Recent Files (how many, how much this browser keeps, Clear Recent Documents). Per-app settings stay in each app's Tools ▸ Options.

 A file dropped anywhere on the page, picked with Open File… or passed by the operating system (installed app, `launchQueue`) goes to the app for its extension (`VO.appFor`); other files get a message in the bar.

Installed (display mode standalone) or in the desktop app, app pages open in a new window and the Start Center stays, as in LibreOffice (`VO.host.newWindow`); in a browser tab they open in the same tab (Back returns).

## Windows

No page draws a title bar of its own: the browser tab, or the system title bar of the installed app, shows `document.title` (`<document> - Quire`). Each app sets its own icon as the page icon with `VO.setIcon(L.icons.app(32))`.

## The host: `VO.host`

What runs the pages, a browser or the desktop app (`desktop/`, Tauri): `VO.host.kind` (`web`, `desktop`), `platform`, `version`, `onFiles(fn)` for files the system asks us to open (the PWA's `launchQueue`, or the desktop app's command line; the Start Center hands them to their app), `openUrl(url)` (a new tab, or the default browser), `newWindow(url)` / `closeWindow()` (an app in a window of its own; File ▸ Exit closes it) and `uiScale()` / `setUiScale(n)` (the desktop app's zoom; `null` on the web). Pages use `VO.host` for anything the two differ in. The interface, its rules and what is planned are in docs/desktop.md (Host interface).

## App launch: `VO.launch` and `VO.attach`

| URL | The app starts with |
|---|---|
| `<app>/` | its sample document, as before |
| `<app>/?new` | a blank document (`Document1`, `Book1`, `Presentation1`) |
| `<app>/?template=<id>` | a new document from that template (`Document1`, `TaskTracker1`, `Presentation1`) |
| `<app>/?open=<id>` | a blank document, then the file the Start Center stored under `id` in the `handoff` store (read once, then deleted; entries older than a day are swept) |
| `<app>/?recent=<key>` | a blank document, then that Recent Files entry |
| `<app>/?doc` | the desktop app's window made for a document: a blank document, then the one the native side gives it (`VO.host.document()`: a file, a Recent Files entry or its unsaved version, bytes another window handed over; docs/desktop.md, Documents and windows) |

The query is removed from the address once read, so a reload starts clean. Opening the file replaces the untouched blank document (each app already does this for its own File ▸ Open), so it ends up in one window.

**Saving.** On the web a save is a download (`L.saveFile`). In the desktop app the apps save to real files through `L.file` (`common/core.js`; docs/desktop.md, Saving): Save writes the window's own file in place when it has one it may change (`L.file.inPlace()`), Save As and every export ask with the system's Save dialog (`L.file.choose`), and `L.file.write` writes and tells a failure with its next step. Each app lists what it saves in `L.file.types` (`{ id, label, ext }`, its Save As dialog's list); its save code takes `how` (`'save'` or `'chosen'`), and `L.saveFile`'s other callers (PDF from Print, mail merge's PDF) are exports there. A document's name, type and changes follow a save only when the file became its own.

File ▸ Exit closes the app's documents (asking to save each; Cancel stays) and calls `VO.exit()`: an app window the Start Center opened (installed) closes, showing the Start Center behind it; a tab goes to the Start Center.

Each app, in its `A.init`, picks template, blank or sample from `VO.launch` and finishes with

    VO.attach('<app>', { open(file, { draft, name, saved }), thumb(), message(text), templates(),
                         snapshot(doc), docInfo(doc), isDirty(doc), current(), autosave(), showRecovery() })

and reports `VO.opened(file, doc)` after any successful open (File ▸ Open, drop, Start Center), `VO.saved(name, blob, doc)` after a save in its own format, `VO.changed(doc)` after an edit and `VO.discard(doc)` when the user drops the changes (Quire `.docx/.dotx`; Ledger everything but web pages and PDF; Lectern `.pptx/.ppsx/.potx`). Every call is guarded with `if (window.VO)`, so an app page still runs on its own.

What each app provides:

- its name on its page's `<html>`: `data-app="quire" data-app-name="Quire"`, which `core.js` reads as `L.APP_ID` and `L.APP_NAME` (no inline script: Security). `APP_ID` prefixes the app's settings (`quire.…`, `L.store`; Settings), so it must never change.
- in its `app.js`, at load: `L.icons.app` (its icon), `ui.hooks = { beforeExec, refocus, commitEdit }` (its editor around commands, toolbar boxes and dialogs); Lectern also `ui.schemeColors` / `ui.currentDesign` (theme colours in colour menus) and PowerPoint's `L.SIZE_LIST`.
- a spelling UI sets `L.spell.refreshSoon` if it draws underlines (Quire).

**Drags.** Every press-and-drag of the apps (moving a shape, a ruler marker, a cell range, drawing a shape, a
splitter) is a `ui.drag(e, { move, up, cancel, threshold, capture })` from `ui.js`: one at a time; `move` only after
4 px, so a click that never moved changes nothing; `up` on the release; `cancel(d, why)` instead, with nothing
committed, on Esc (which also ends the tool and puts a brush down), Ctrl+Z or Ctrl+Y (the drag is what gets undone), a
second button (its menu doesn't open), a release the page never saw, a lost capture, the window losing focus or
`ui.dragCancel()` (a tool, view, sheet, slide or zoom switch); a tool stays armed after the other cancels. Other keys
go nowhere while the button is held (the modifiers still shape the drag), and each app's history push (Quire `D.tx`,
Ledger `O.tx`, Lectern `L.hist.push`) cancels a live drag before it records, so no edit comes between a drag's start
and its step. The cursor of the press stays while the pointer moves (`cursor: false` holds none). The browser's own
text-selection drags stay its own; Quire watches its text selections with a `ui.drag` that holds nothing
(`{ capture: false, cursor: false }`), so a selection let go in another window or cut short by Esc or a second button
ends without `'sel-done'` (`tests/ui/drag.test.mjs`, `tests/ui/gestures.test.mjs`; todos/UI_MOUSE_LOGIC_IMPROVE.md).

**Selections.** Each app has one setter for its selection, and it ends the other kinds: Quire's `E.setSel` ends an
object selection (`E.selectObject` is the one way into one, `E.clearObjSel` the one way out), Ledger's `G.select`,
`G.selectRange` and `G.selectAll` end a drawing object's, Lectern's `E.select` ends text editing and a range of table
cells. Lectern's `E.endInteraction()` ends what is under way on the slide (a drag, a freeform, a cell range) on a tool
switch, another slide and undo.

**Focus.** The keyboard stays with the document unless the user picks a control of its own. A press on chrome with
none (a toolbar's, the ribbon's or a pane's background, a grip, the status bar, a tab strip), on a menu, the menu bar
or a button outside a dialog keeps it where it is (one `mousedown` listener in `ui.js`). A dialog closing gives it back
to what had it, editable text with the selection it had (Lectern's speaker notes), except the document's own text
(`ui.hooks.ownsText(el)`: Quire's page, Lectern's slide), which the app's `ui.hooks.refocus()` gives back with its
model selection (Quire `E.refocus`, Lectern the text at `L.te.lastSel`, the slide or the Slides pane); a menu command
that leaves it nowhere calls `refocus()` too (`tests/ui/focus.test.mjs`).

**Hyperlinks.** The suite never opens a document's hyperlink itself: a link in a file can lead anywhere. Ctrl+click (⌘+click on a Mac), Open Hyperlink and a click in Lectern's slide show call `ui.linkDialog(url)` (`common/ui.js`), which shows the address as written with a warning and Copy Address, to paste into the browser's address bar (for `mailto:`, into an e-mail program). Links within the document still go there: Quire's bookmarks (`L.ed.followLink`), Ledger's cell references (`A.followLink`), Lectern's slide jumps. Over a full-screen slide show, dialogs and menus attach inside the full-screen element, where they can be seen (`tests/ui/hyperlinks.test.mjs`).

**HTML we write.** Save as Web Page and the HTML put on the clipboard are documents of their own, opened later
away from the suite's pages, so document data goes into them as text, never as markup: `L.esc` for text and
attributes (style attributes included: they hold font names and colours), `L.cssString` for a font name in CSS, links
only for http(s), mailto and bookmarks, and data inside a page's script as JSON with `<` escaped (Lectern). Each
exported page carries its own Content-Security-Policy, `L.exportCSP(script)` (`common/core.js`): pictures and fonts
from inside the file, no requests, and no script but the page's own, allowed by its SHA-256
(`tests/hostile/export-html.test.mjs`).

**Brushes.** The Format Painter of each app, and Quire's highlighter, is a `ui.brush({ el, pick, apply, hint, status })`: a click on its button arms it for one use or puts it down, a double-click keeps it on, Esc puts it down, and one brush is on at a time. Arming it changes nothing else: the selection and the text being edited stay. It paints once, when the mouse is let go, never while a selection is still being dragged out: the app calls `brush.release()` then (Quire on the editor's `sel-done`, Ledger at the end of a cell drag, Lectern at pointer up in the slide editor) and its `apply` paints what was marked. What the apps paint follows Office and LibreOffice's Clone Formatting (Writer, Calc, Impress): a click inside a word paints the word; Ledger tiles the source range over a larger target; Lectern carries the text's formatting from text being edited and the whole object's otherwise, paints the text dragged over in any box and the whole object when the press is beside its text, and a click beside the objects puts even a kept-on painter down. The painted formatting replaces the target's own; links, fields and revision marks stay (`tests/ui/painter.test.mjs`).

Version: `VO.VERSION` in `suite.js` is the one version string (`L.VERSION` reads it); it says `dev` in the repository, the desktop app's build sets it, and the published copy stamps it. The format is `v<yyyy>.<mm>.<dd>-<6 hex>`, the date (UTC) and commit of the tree (`tools/current-tree-version.sh`, e.g. `v2026.10.11-d2134d`; copies before said `2026.10.8f8494`). `VO.compareVersions(a, b)` compares two by their dates alone (negative, 0, positive; `dev` is newer than any dated version, an old-format one counts as day 0 of its month). `VO.monthsOld(v, now)`: a version's age in whole calendar months (null for `dev`); `VO.isOutdated(v, now)`: whether it is two or more, for Check for updates. The Start Center (under its privacy note, and in About) and each app's Help ▸ About show it; Help ▸ About and the Getting Started pane name the edition too, in English in every language (`VO.editionName`: Quire Web Edition, Windows Edition, macOS Edition (DMG) or (App Store), Linux Edition). `public/updater/current.json` names, per policy and platform, the oldest version that needs no Update button or dialog, and `public/updater/whatsnew.json` what each version brought, for the Update dialog (docs/desktop.md, Versions and updates).

## Security: the pages' policy

Every page carries one Content-Security-Policy, as a `<meta http-equiv>` first in its `<head>`, so it travels with
the files: the site, the PWA's offline copy (the service worker serves it from its cache, where a server's header
never reaches), the desktop app's pages and the local tests. `tools/csp.mjs` holds it and writes it into the pages
and the sources other tools build pages from (Ledger's template, `tools/oss-licenses.py`); `--check`, run by
`tests/csp.test.mjs`, fails on a page without it or with an inline script, an `on…=` handler or a `javascript:` URL.

    default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
    font-src 'self' data:; connect-src 'self' data: blob: https://vibeoffice.work ipc: https://ipc.localhost;
    worker-src 'self'; manifest-src 'self'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'

- **Scripts:** our own files only. The browser refuses inline scripts and handlers, `eval` and `new Function`, and
  `javascript:` URLs. So no page has an inline script: the look is `common/look.js`, the Start Center's code
  `start.js`, the licences page's `oss-licenses.js`, and an app names itself on `<html>` (`data-app`). Code that
  needs a handler adds it with `addEventListener`.
- **Styles** may be inline (`style` attributes are everywhere, and CSS can run no script). Pictures, fonts and data
  come from the site or from inside the page (`data:`, `blob:`).
- **Connections:** the site, the update check (`https://vibeoffice.work`), and the desktop app's IPC (`ipc:` on macOS
  and Linux, `https://ipc.localhost` on Windows). On Windows this also closes WebSockets, which WebView2's request
  filter may not see (docs/desktop.md, Network).
- **`form-action 'none'`:** the Start Center's `<form method="dialog">` only closes its dialog, which isn't a
  submission the policy governs.
- **To add a source:** change `POLICY` in `tools/csp.mjs`, run it (it rebuilds Ledger's page), and run
  `python3 tools/oss-licenses.py`. Say why here.

What the policy doesn't cover:
- **Navigation:** where the window goes, or a window it opens. Document links never navigate (Hyperlinks, above), and
  the desktop app opens only our own addresses in the browser (docs/desktop.md).
- **The service worker:** a worker takes its policy from its script's response headers, not from a page.
- **Files we export:** they carry their own (HTML we write, above).

Tests see a refusal: `tools/shot.mjs` fails on one, and the UI tests' `t.clean()` does too, and on a window the page
opens or a page of another site in the tab (`tests/hostile/helpers.test.mjs`). Chromium itself reports a refusal
only to its Log domain, so both listen for `securitypolicyviolation` in the page.

## Settings

`VO.settings` (`common/look.js`, the first script of every page) holds the suite's settings, strings by key as `localStorage` keeps them: `get(key, default)`, `set(key, value)` (null removes it; false if it can't be kept), `remove(key)`, `on(fn)` (`fn(key, value)` when another window changes one; key null: all may have) and `kept()` (resolves once this page's changes have reached the desktop app: before a reload). Keys are `<app>.<name>`: `vibeoffice.…` for the suite (`look`, `lang`, `localFonts`, `updateAsked`, `assistant`; `uiScale` in the desktop app), `scout.…`, and each app's `L.store` values, JSON under `<APP_ID>.<name>`. On the web they are the browser's `localStorage`, whose `storage` event tells the other windows; in the desktop app `~/.vibeoffice/config.json`, which the app serves with `look.js` and keeps current in every window, and the pages have no browser storage at all (docs/desktop.md, Settings and storage). Only the web branches of `look.js`, `suite.js` (Recent Files, the service worker) and `start.js` name browser storage (`tests/desktop/host.test.mjs` checks).

## Looks

The chrome (menus, toolbars, task panes, dialogs, status bar, rulers, sheet headers) can be drawn in more than one look: **Classic** (Office 2003 blue, the default), **Paper** (warm light chrome with one teal accent and rounded shapes) and **Paper 2016** (Paper's colours with a ribbon of tabs instead of the menu bar and toolbars, see The ribbon). The user picks one on the Start Center (Themes, beside About: a card per look, its preview drawn from that look's settings via `data-look` on the card) or in Tools ▸ Options ▸ General ▸ Theme of any app; it applies to the whole suite and every open window at once.

- `common/looks.css` holds every chrome colour, font and shadow as a named setting (`--chrome-line`, `--pane-ink`, `--btn-a`, `--hdr-sel-a`, …), one block per look keyed by `data-look="…"` (on `<html>`, or on any element to preview a look inside another); Classic's block is also `:root`, the default. Paper adds a few shape rules a colour cannot express (rounded trays, pill tabs), scoped `:is([data-look="paper"], [data-look="paper2016"])`; Paper 2016 shares Paper's block and adds nothing of its own but the layout. `ui.css`, each app's CSS and the Start Center use only these settings for chrome.
- Only chrome is themed. Document content (pages, cells, slides, comments, revisions, objects and their handles, Excel's in-cell buttons), icons and colour swatches keep their colours in every look.
- Each page's head loads `common/look.js`, which sets `data-look` from the setting `vibeoffice.look` (Settings; default `classic`, the desktop app's Paper) and `data-layout` (`ribbon` for Paper 2016, otherwise `bars`) on `<html>` before the stylesheets load, so a page never flashes the wrong look. The key is suite-wide (not `L.store`, which is per app).
- `VO.look` (`suite.js`): `list()` (`[{ id, name, note, layout }]`), `get()`, `layout()` (`'bars'` or `'ribbon'`), `set(id)`. `set` saves the choice, switches this page, updates `<meta name="theme-color">` from `--theme-color` and fires `vo-look` on `window`; other windows switch when they hear of the setting (`VO.settings.on`). `ui.lookField()` is the Options dialogs' Theme drop-down.
- Chrome drawn on canvases reads settings with `L.lookColor(name, fallback)` (cached, cleared on `vo-look`) and redraws through `L.onLook(fn)`: Quire's and Lectern's rulers, Ledger's row and column headers and cell selection (`RD.lookColors`). Ledger's gridlines, frozen-pane lines and page breaks are the sheet's own.
- To add a look: copy Classic's block, give it a new `data-look` name and values, add it to `LOOKS` in `suite.js` (with `layout: 'ribbon'` for a ribbon look; `common/look.js` names the ribbon looks too). `node --test tests/looks.test.mjs` checks that every look sets every setting, that every setting the chrome uses exists and that `ui.css` has no colours of its own.

### The ribbon

In the Paper 2016 look each app shows a ribbon in place of the menu bar, toolbars and drawing bar (hidden by `[data-layout="ribbon"]` in `ui.css`); the view buttons, status bar and task pane stay. It follows Office 2016's arrangement and command names; the icons, colours and wording are our own (it is called the Paper 2016 look in the UI, and the box is "Search commands").

- `common/ribbon.js` (`L.ribbonUI`) draws it from the app's `js/ribbon.js`, which sets `L.ribbonSpec = () => ({ icons, qat, file, tabs, contextual })`. It is built the first time a ribbon look is in use (`L.ribbonUI.init()` after the app's toolbars, then `L.onLook`), so Classic and Paper never build it.
- A tab is `{ id, label: '&Home', groups: [{ label, icon, launcher: cmdId, items }] }`. Items: `'cmdId'` (small button), `{ cmd, size: 'large'|'medium', label, icon }`, `{ split: cmdId, menu: (rect, el) => … }`, `{ drop: label, icon, menu }`, `{ make: () => element }` (a combo box from the app's `A.parts`), `{ row: [...] }` (a row of small buttons, as in the Font group) and `'|'` (a new column). Buttons are `ui.tbButton` / `tbSplit` / `tbDrop`, so enabled, checked and colour swatches update through `ui.refresh` as on the toolbars. `icons` gives an icon to commands that have none of their own; large buttons scale the 16 px icon to 32 px.

A set opens when it appears while the Insert tab is showing (the object was just inserted) or when it has `open: true` (Header & Footer, Outlining, Slide Master); when it goes, the tab used before it comes back.
- **The task pane follows the selected object** in every look (`RB.follow` in `common/ribbon.js`, set up by each app after its task pane). The contextual sets about objects are also task-pane panels with the same groups and commands in one column (`RB.toolsPanel`): Lectern's Picture, Drawing, Table and LettersArt Tools (an IntelliArt diagram keeps its text pane), Quire's Picture and Drawing Tools, Ledger's Chart, Picture and Drawing Tools. While the task pane is open, selecting such an object shows its panel, and selecting nothing goes back to the pane shown before. It never opens the task pane itself; a pane that its object opened (IntelliArt's text pane) closes again with it. It stays put in narrow windows (where the pane covers the document), for text, cells and tables in a document or sheet, and when the user turns off Tools ▸ Options ▸ View ▸ *Task pane follows the selected object* (`paneFollows` in the app's options).
- File opens the app's File menu (`file()`, command ids) as a drop-down, ending with Options, Help, About and Exit, since the ribbon has no Tools or Help menu.
- Keyboard: Alt or F10 shows KeyTips (numbers on the Quick Access Toolbar, the access letters on the tabs); a tab's letter opens it and shows one or two letters on each command (`ui.barKeys` routes the menu bar's keys here). Esc goes back a level. Ctrl+F1 collapses the ribbon (as does a double-click on a tab or the arrow at the right, remembered per app as `ribbonCollapsed`); a tab then opens over the document. Task Pane, Ctrl+F1 in the other looks, is under View ▸ Show.
- In a narrow window the groups fold from the right into one button each that opens the group below it.
- Adding a command to an app: put it in that app's `js/ribbon.js` too, where Office has it. `node --test tests/ribbon.test.mjs` (needs Chromium, as `tools/shot.mjs`) checks in each app that every command id in the ribbon exists, every button has an icon, and every command of the menus can be reached from the ribbon, apart from a short list of exceptions kept in the test.

### Search commands

Every app, in every look, has a Search commands box at the top right (the end of the menu row, or the ribbon's title row): the way to find a feature by name. Alt+Q goes to it, as in Office.

- Typing lists up to ten of the app's commands, best first, each with its icon, its shortcut and where it lives in the current layout (`Format ▸ Font`, `Formatting toolbar`, or with the ribbon `Home ▸ Font`, using the ribbon's own label for the button); commands that cannot run now are greyed. Arrow keys move, Enter or a click runs one, Esc clears the box and then goes back to the document. With nothing typed it shows the commands last run from it (`searchRecent`, per app).
- A word matches a command's name as a whole word or the start of one (compound names split: AutoSum answers to "sum"), with one typo ("hyperlnk"), or through an everyday word for Office's name (`SYN` in `search.js`: image → Picture, margins → Page Setup, synonym → Thesaurus, pdf → Save As). A command in a submenu also answers to the submenu's name (Insert ▸ Picture ▸ From File for "picture"); the tooltip and location count for less. Every word typed must match.
- `ui.searchBox()` makes a box; `ui.searchCommands(query, layout)` gives the ranked list. The menu paths come from `ui.menus` (set by `ui.menuBar`), the toolbars from the page, the ribbon places from `L.ribbonSpec`. There is no app-specific code: a new command is found once it has a label, and shows its place once it is in a menu, toolbar or the ribbon.
- `node --test tests/search.test.mjs` (needs Chromium) checks, in each app and both layouts, that everyday words find the intended command first and that it says where it is.

Script order: `suite.js`, the app config, `core.js`, then the libraries and the app's own scripts as listed in each `index.html` (Ledger's from `tools/ledger/build/make.py`, where `'common/x'` means `public/common/x.js`).

## The assistant: Scout

Scout, a beagle on his mat, is the suite's assistant, and the place where an AI assistant will live later; for now he offers a few things to do. He is in every app, in every look, and comes in when an app starts, except on iOS and Android (`L.isMobile` in `core.js`) and in an automated browser (`navigator.webdriver`: Playwright, and `tools/shot.mjs`, which says so), where he comes in only once the user has shown him. Hiding him lasts the day: he doesn't come in by himself again until the next day.

- **Help ▸ Show the Assistant** (`showAssistant`, defined by `assistant.js`; it reads *Hide the Assistant* while he is shown) brings him in at the bottom right with a wave (Greeting), nothing said, except the first time he is shown each day (from the menu, or when an app starts with him): then he waves, says good morning, afternoon or evening by the clock, introduces himself and asks what the user would like to do: *Good morning! I'm Scout, your soon-to-be-AI assistant. For now, I mostly fetch. What would you like to do?*, with choices: Find a command by name (points at Search commands and puts the cursor in it), Look something up in Help, Get started, See the keyboard shortcuts (each only where the app has that command), Show me a trick, Nothing for now. Coming in by himself once he has greeted today (another app, the next start), he just pops in (Show), with nothing to say. A click on him asks *What would you like to do?* with the same choices (or closes the balloon); he can be dragged anywhere. A click leaves the keyboard focus in the document.
- **Right-click** (or Shift+F10 on him) opens the app's own menu: Animate! (a random action), Search commands (as the first choice), the app's Help and, last after a separator, Hide. Hide, like Hide the Assistant, plays GoodBye: he waves and drops through his mat (turned off in another window, he goes at once).
- Kept for the whole suite in the settings (`VO.settings`), as the look is: `vibeoffice.assistant` (`{ on, r, b }`: whether the user last showed or hid him, and his distance from the window's right and bottom), `scout.lastGreetedDay` (the last day he said good morning) and `scout.lastHiddenDay` (the last day the user hid him; showing him clears it). Days are local dates (`2026-10-11`) and are only compared for equality, so a clock set back never keeps him away or skips a greeting. An app starts with him when it isn't the day he was hidden and either the user last showed him or the platform has him by default. Showing or hiding him in one window does so in the others (`VO.settings.on`).
- **While the user works** he acts out what they ask for, as they ask (the command, or the dialog it opens), from signals the shared code sends anyway (events on `window`): `vo-command { id, result }` after `ui.exec` runs a command, `vo-message { icon }` when a message box opens (`ui.js`), plus the browser's `beforeprint`; `vo-busy { on, text }` (the busy box coming or going, `ui.js`) keeps him at it. Saving is the exception: he saves once the file is written, on `vo-saved { name }` (`L.saveFile` in `core.js`, once the file is handed over) after a save command (Save, Save As, Save as Web Page, PDF or CSV export); a PDF written after Print is no save. The apps don't call him. The pairings are Office's (`msoAnimationSaving`, …), in `ON_COMMAND` in `assistant.js`:

  | What the user asks for | He plays |
  |---|---|
  | Save, Save As, Save as Web Page, PDF and CSV export: once the file is written | Save |
  | Print, Print Preview; the browser printing | Print |
  | Open, Slides from Files, Insert File, Import Text | Fetch |
  | Find, Replace, Go To, Research, Thesaurus | Searching |
  | Spelling, Error Checking, Word Count, Compare, formula auditing | CheckingSomething |
  | Send Mail | SendMail |
  | a comment, footnote or speaker notes | Writing |
  | deleting a slide or sheet, all comments, Clear All | EmptyTrash |
  | a picture, clip art, LettersArt, IntelliArt, chart, media, design, background | GetArtsy |
  | AutoSum, functions, fields, macros, recalculation, Goal Seek, scenarios, PivotTable and other data tools | GetTechy |
  | Mail Merge, the wizards, AutoFormat, animation schemes | GetWizardy |
  | a warning or error message box | Alert |

  Work keeps him at it: if the busy box is still up when his act ends (a long save after Save), he carries on (Processing) until it goes; a wait longer than 0.4 s with no act of his (opening from Recent Files) has him work along the same way. Manners: he acts only while he is on screen and the window is in front; never while he is asking something (a balloon is open) or coming and going; an idle gives way at once, and a nap ends first with his waking up; an earlier act plays out, and one act waits for it (a newer one takes its place: `play(act, { next: true })`); the act he is at already, nothing new; nothing with reduced motion. A new pairing is a command id added to the table.
- **Idling** follows the user: their keys, clicks and wheel, and the window coming back to the front, tell him they are at work (`scout.userActive()`, from `assistant.js`); the mouse merely moving does not. While they work he does a small thing 45–90 s after his last act (a glance, an ear flick, a slow blink, a look at their work, tail thumps, …; never one of his last two); once they have been quiet for 30 s, every 8–16 s; after two minutes, bigger ones (scratching, tapping, the atom, the rope); after five minutes he naps (IdleSnooze, looping) until they are back, and wakes with a start. His time counts only while the window is in front. The stages are `IDLE_STAGES` in `scout.js`.
- **At rest** he sits still, and nothing is drawn: no breathing, no sway of the head. Now and then he blinks (every 4–9 s, sometimes twice, every frame for 0.2 s), and every 11–25 s his tail sways slowly for 3 s at about 10 frames a second, as his nap is drawn; an action, a word or a move has every frame. Each frame says when the next is needed (`_wait`), and in between nothing runs but a look at the time once a second, for idling.
- **Energy:** the frame loop runs only while something moves. Measured in Chromium: at rest about 0.1% of a CPU core, asleep about 3%, while he acts about 9% (60 frames a second). While the window is in the background (blurred for more than 250 ms) he stands still and nothing is drawn (`scout.freeze(true)`); he carries on when it comes back. A hidden page draws nothing anyway. Once hidden, the loop stops altogether. A frame costs about 0.2 ms of script; most of the rest is the browser painting the picture.
- **The character** (`scout.js`, `L.Scout`) is an SVG rig posed procedurally every frame, no image files: all 43 actions of the Office assistant agent under their names (Greeting, Searching, GestureUp, …), the 35 Office 2003 `msoAnimation…` constants as aliases, and 24 actions of his own (9 of them small idles for while the user works: an ear flick, licking his chops, a slow blink, settling on the mat, tail thumps, a curious tilt, a look at the user, a glance at their work with a nod, a small yawn); one camera angle, three-quarter (facing the user is a turn of the head, as in IdleLookAtYou). Calls queue: `show`, `hide`, `play(name, { loop, until })` (`interrupt`: now, in place of everything; `next`: once the act under way ends, one waiting at most), `speak(text)`, `ask(text, choices)` (resolves with the choice picked, or null), `gestureAt` / `lookAt(x, y)`, `animate`, `moveTo`, `delay`; `stop`, `freeze`, `placeAt`. Options `onclick`, `onmenu(x, y)` and `onmoved(x, y)` hand clicks, the menu and drags to the user of the character (`assistant.js`), so it has no menu or storage of its own.
- His colours are his own in every look; the balloon is chrome, drawn like a tooltip from the look's settings (`--tip-bg`, `--tip-line`, `--tip-link`, `--ui-font`) in `scout.css`, which `tests/looks.test.mjs` checks with `ui.css`. He sits above the document and task pane (z-index 900), under menus and dialogs.
- `L.assistant`: `show(welcome)`, `hide()`, `shown()`, `scout()` (the character, for later uses such as answers in the balloon). Office 2016 has no assistant, so he has no place in the ribbon; Search commands finds him ("assistant", "scout").
- `node --test tests/scout.test.mjs` (needs Chromium; serves on :8775 of its own, so apps open on :8760 don't answer its changes to the shared settings) checks each app: the Help menu item, the welcome's choices, the menu, acting out Print, Find and saving (once the file is written, not when asked, not after Print), with manners (one act waiting, the newest; a nap ending before a save), and working along with a long wait, the idle stages (none straight after an act, small ones while the user works, a nap after five minutes that a key ends and moving the mouse doesn't), no frames at rest but a blink and the tail's sway (about 10 a second, as asleep), every frame acting, none in the background or once hidden, that nothing of his own (ears, the head's outline, his body or collar tag) covers his eyes, nose, muzzle or tongue in any action (hit-tested every 0.1 s), and the kept settings; and in Quire when he comes in by himself (a desktop yes; an iPhone, an automated browser, the day he was hidden no).

## Preservation

Same-format Office saves carry what the model cannot edit. These contracts apply to all three apps;
the current feature and edit-behaviour tables are in [Quire](quire.md#what-a-save-keeps-converts-and-drops),
[Ledger](ledger.md#what-a-save-keeps-converts-and-drops) and
[Lectern](lectern.md#what-a-save-keeps-converts-and-drops). Conversions to Markdown, CSV, PDF and other
formats have their own rules.

- OOXML preservation uses `common/opc.js`: immutable package bytes stay outside JSON history; model fragments carry source identities and dependency references. Classify parts as opaque, merged or regenerated. Preserve original identities unless every referrer is regenerated; duplicates remap definitions and references together. Merge settings-like parts only; regenerate content parts with model-attached fragments. Record conversions and drops in the document's loss ledger.
- Save and drafts keep the main-part variant and encryption. Save As changes the filename/type only after a successful download. Show the unacknowledged entries marked `notify` in the Compatibility Checker after preparing the file and before download (see [What the user is told](#what-the-user-is-told)); acknowledge only a successful user save. Drafts neither show nor acknowledge the checker. Recompute writer losses on every save so cancelling a conversion does not poison the next save.
- Preserved content-control boundaries and binding updates participate in undo. Keep boundaries balanced through edits and paste, remap copied identities together, and roll back the whole transaction when a content/deletion lock forbids it. Typed value commands retain their binding; ordinary typing that converts a typed control records that conversion.
- Retained formatting belongs to individual properties: compare the owning model fields, replace only the property the user changed, and keep its siblings. Capture property alternatives before normalisation and emit changed children in Office-compatible schema order. Copy range endpoints together with fresh identities; report incomplete ranges at save.
- Rewritten parts hoist repeated namespace declarations. Keep a minimal local `mc:Ignorable` list when a scoped `PreserveAttributes`, `PreserveElements` or `ProcessContent` rule requires it; moving that processing rule to root would widen its scope.
- Opaque frames belong to their displayed objects. A compatibility wrapper with several model members is emitted once only while all members remain intact, ordered and contiguous; never resurrect deleted content. Geometry updates preserve the payload. Clipboard transfer includes preview bytes, dependent parts and implicit references, with copied definitions and references remapped together.
- Preservation changes are measured against the pinned corpus (`tools/corpora.sh`), including edits, undo/redo and drafts. Record failed and excluded attempts, compare validator diagnostics with each original, and keep Office acceptance pending until it has actually been checked. The measurement tools are in `tools/ooxml/`.

| Part ownership | Writer contract |
|---|---|
| Opaque | Carry original bytes and original relationships; follow their dependency graph, including cycles and shared targets |
| Merged | Start with the original settings-like part and replace only model-owned properties in schema order |
| Regenerated | Write model content and attached fragments; preserve identities used by any retained referrer |

Strict inputs save as Transitional OOXML with a recorded conversion entry (not shown: Office reads both alike). This explicitly
converts retained XML namespaces and vocabulary; binary dependencies remain unchanged. It preserves
the document/template/slideshow and macro variant.

`L.opc.open` reads the immutable baseline; `attach` keeps it out of JSON snapshots. `fragment` records
namespace context, relationship attributes and identity definitions/references. `captureAC` runs on
the original XML before branch selection, and `emit` writes an outer compatibility record once.
Inherited compatibility attributes are merged by namespace URI and local name, even when an ancestor
and a fragment use different prefixes. Repeated saves must not add a second `Ignorable` attribute
under an alias; the fragment keeps its own spelling and the inherited value list.
Fragments stay self-contained in history and clipboard data. Once a regenerated or merged part is
assembled, `output.put` hoists missing namespace declarations and the union of `mc:Ignorable` onto
its root. It removes redundant inner declarations, keeps actual prefix rebindings and default-namespace
resets, and leaves other compatibility properties scoped as written. Opaque parts bypass this pass
and keep their bytes. This prevents every preserved paragraph/run property from repeating the full
document namespace list.
`patch` assembles disjoint source slices once, so namespace cleanup does not copy a large part
for every removed declaration. Insertions at shared boundaries retain their original order.
`duplicate` assigns a shared copy identity to the selected definitions and references; `export` and
`import` transport their dependency bytes between documents. The writer reserves existing part names,
relationship IDs and identity spaces before allocating new values. Master and layout IDs share one
space; non-empty preset adjustment lists include every preset value in Office's order.

GUID-bearing models opt into `duplicate` with `guidAttributes` and `guidFields`. Supply `guidValues`
to identify definitions explicitly when some fields refer to shared people or other shared objects.
`guidSources` includes definitions in separately written XML parts; `guidMap` receives their shared,
JSON-safe mapping. Copies allocate these IDs during the edit, so undo, drafts and repeat saves keep
the same IDs. `remapGuids` applies that mapping when the app writes a dependent part. It changes
identity attributes only: relationship IDs, text, URLs and extension URIs keep their own meaning.

The loss ledger distinguishes conversion from deletion and keeps stable entry identities. Specific
object conversion/deletion notices can account for their opaque dependency trees with `coverLoss`;
this suppresses redundant part notices without removing any parts or crossing rewritten-content
boundaries. Unexplained missing parts still produce their own loss entries. Digital
signatures are removed and reported because a changed package cannot retain their validity. Missing
dependencies and unavoidable conversions are reported by the writer; draft recovery retains pending
entries even when the original content has already been converted in the draft.
`output` runs its app-owned audit after assembling content. `reportFeatures` compares specified
features in regenerated parts, so retained wrappers do not warn merely because the reader uses a
simpler model. Chart/drawing regeneration and notes-page formatting conversion report at their
writer branches. Cancelling a conversion and then saving the original representation clears its
save-time notice; only a completed download acknowledges current notices.

### What the user is told

Every entry is recorded (corpus drivers and tests read `doc.losses`), but the Compatibility Checker
shows only entries with `notify: true`: the user loses content or a working feature. That covers an
object removed, SmartArt/OLE/ink saved as shapes or a picture, a slicer, control, comment thread or
media that stops working, macros or a signature removed, pivot cells Office will overwrite, and parts
of a damaged file that could not be read. Silent: repairs of damaged or invalid input that keep the
content, format normalisation (Strict to Transitional, pre-release markup), formatting details behind
an edit the user made, objects the original already lacked a part for (`L.opc.sourceMissing`), and
audit catch-alls. The unreferenced-part and `reportFeatures` entries are bug alarms for corpus runs:
a real loss should get its own notice where it happens.

Shown entries are plain sentences about the user's content ("This IntelliArt will be saved as ordinary
shapes, because it was edited here."), with `place` in the user's terms (a sheet, cell, slide or
control name). Part names and error text go in `where` and `detail`, never in the dialog. The dialog
groups identical messages and lists their places.

An Office review batch contains at most 15 files and a checklist. Before handoff, compare the new save
with the previous writer's save of the same input and explain each difference. Automated validators
and LibreOffice do not establish Office acceptance. Keep run history outside the repository in
`~/corpora/results/<run>/README.md`, and keep app docs focused on current behavior and measurements.

## Recent Files and unsaved versions

One list for everything a user worked on, shown in four places: the Start Center (cards), each app's File menu (1–4), its Getting Started pane (Open) and its Document Recovery pane. Every entry really reopens.

IndexedDB database `vibeoffice`, store `recent`: `{ key, app, name, size, time, file, thumb, draft }`, keyed `<app>:<file name>`, or `<app>:~<id>` for a document that was never saved. The browser has no file paths, so the list keeps a **copy of the file**: `file` is the one opened or last saved; `draft` (`{ file, name, time, lossState }`) is the **unsaved version**. Two files with the same name in different folders share an entry. At most 30 entries, but an entry with unsaved changes is never dropped; files over 50 MB are not kept. Every page hears about changes over the `BroadcastChannel` `vibeoffice` (`VO.onRecentChange`); `VO.recent.cache` is the list for menus.

**Keeping the data.** Safari clears a site's data after about 7 days without a visit; the first time a document's unsaved version is stored, `navigator.storage.persist()` asks the browser to keep it (Safari and Chrome decide without asking the user). Where IndexedDB is missing (Safari's Lockdown Mode), the Start Center shows an alert explaining how to turn Lockdown Mode off for the site.

**Autosave.** The app calls `VO.changed(doc)` when a document changes; 15 s after the last change `hooks.snapshot(doc)` writes it in the app's own format (including macro, template and slideshow variants; password-protected documents stay encrypted) into the entry's `draft`. `VO.opened(file, doc)` and `VO.saved(name, blob, doc)` tie the document to its entry; saving clears the draft (and retires the `~` entry of a never-saved document); No in "Do you want to save the changes…?" calls `VO.discard(doc)`, which throws the draft away. Closing the tab or a crash leaves it. To spare the disk, a document's unsaved versions are at least 2 minutes apart (a save counts as one), a large document's 12 s for each MB (50 MB: 10 minutes, as Word's AutoRecover) and a slow one's 30 × the time the last write took; typing on doesn't put one off for longer than that. One over 50 MB isn't kept: the app says so once (a toast), then only tries again after that gap. Draft metadata also keeps pending and acknowledged compatibility entries; recovery restores them silently so the next user save can report an earlier conversion. Quire's Tools ▸ Options ▸ Save ▸ "Save AutoRecover info" turns it off.

**Recovery.** When an app starts and other documents of it have unsaved versions, it opens the **Document Recovery** task pane (as in Office 2003): each one with *Open the unsaved version* and *Discard the changes*. Opening one (`VO.openRecent(key, { draft: true })`, or `<app>/?recent=<key>&draft` from the Start Center) restores the changes as unsaved, so the document still has to be saved; a never-saved one then asks for a name. On the Start Center such a card is marked *Unsaved changes* (or *Never saved*), opens the unsaved version, offers *Saved version* when there is one, and × discards the changes.

**The desktop app** keeps the list itself, in `~/.vibeoffice` (docs/desktop.md, Documents and windows), one entry per file (by its path), with no copy of the file: `VO.recent.list()` comes from the native side, with `saved` (it has a file), `folder`, `preview` (`VO.recent.preview(e)` gets the picture), `open` and `here` (open in a window, this one), and `vo-recent` says when it changes. Only the Start Center lists them, opens them (a window of its own) and discards their unsaved changes; in an app the File menu's Recent Files..., the task pane's link, the Document Recovery pane and `VO.openRecent` bring the Start Center forward on them (`VO.host.showRecent`), and the app page reads no entry. A window's draft and picture go to its own entry, never by key (`VO.changed`, `VO.discard`, `VO.saved`). File ▸ Open in an app window replaces its document by reloading the window with the file picked, after the "Save changes?" question (`VO.openDialog`, docs/desktop.md).

Thumbnails are JPEG, at most 320 px, made 0.6 s after an open, a save or an autosave of the current document from `hooks.thumb()`: Quire rasterizes its first page as for PDF (print layout only, with only the pictures on that page), Ledger crops the top left of its grid canvas (4:3, at most 600 px wide), Lectern draws slide 1. Without one, the card shows the app's page picture and the extension.

## PWA

The manifest's `id`, `start_url` and `scope` are `./`, so the suite installs from any folder it is served from. The Start Center's Install button, and the browser's own install prompt, are offered only on https://vibeoffice.work and 127.0.0.1 (`VO.offersInstall`). Shortcuts create a new document, spreadsheet or presentation (`<app>/?new`). File handlers (`.docx .dotx .docm .rtf .md .markdown`, `.xlsx .xltx .xlsm .csv`, `.pptx .ppsx .potx`) all go to the Start Center, which hands the file on; `launch_handler` `focus-existing` reuses an open Start Center window. ## Service worker

`public/sw.js` caches the published site for offline use. It works only on https://vibeoffice.work/ and on 127.0.0.1 (any port, to try a published copy locally: docs/testing.md): `common/suite.js` registers it there (scope `/`, `updateViaCache: 'none'`, so the browser always asks the server for `sw.js`) and removes any earlier registration anywhere else (localhost, preview deployments). On the dev server (`tools/serve.py`, 127.0.0.1:8760) the files are unstamped (`VERSION = 'dev'`), so the worker is registered but caches nothing and answers no request: local work never meets a cache. The desktop app has none.

**Publishing.** First the whole UI suite, `node tools/ui-full.mjs` (docs/testing.md); both scripts below warn when it has not passed on this `public/` (`tools/ui-tested.sh`). `../cf-vibeoffice/sync-cf-pages.sh` copies `public/` and runs `tools/web-release.sh <copy> <version>`, which stamps the version (`tools/current-tree-version.sh`) into the copy's `common/suite.js` and `sw.js` and packs `updater/web-<version>.zip` (Info-ZIP `zip`): every file but `sw.js`, `updater/` and hidden files, about 4.4 MB for the 10.5 MB site. The changed `sw.js` is what makes browsers install the new worker. In the repository `VERSION` stays `'dev'`, and an unstamped worker caches nothing.

**Install.** The worker downloads the version's zip, the whole site in one file (so one consistent version, whatever the server does meanwhile), and unpacks it into the cache `vibeoffice-<version>` with the apps' own ZIP engine (`importScripts('common/zip.js')`: the browser's inflate where there is one, its JavaScript inflater otherwise), each file checked against the size and CRC-32 in the zip's central directory and given the `Content-Type` of its extension. The whole site is cached, the dictionaries too, so spelling works offline; every update downloads the whole zip again. Anything failing (offline, a download shorter than its `Content-Length`, a damaged zip or one the reader had to repair, a name the site can't have, storage full) fails the install: the half-filled cache goes, the earlier worker goes on serving, and the browser tries again on a later visit. Old caches are deleted only after the new worker has activated, never during install: until then the earlier worker still serves the open pages from its cache.

**One version per page.** Each page is served from the cache of the version it was loaded with (the cache `vibeoffice-clients` records page → version), so an app page open while an update lands goes on loading scripts of its own version, never a mix (the apps load 20–45 classic scripts that must match). Navigations get the newest version. So the new worker takes over at once (`skipWaiting`, `clients.claim`) with no "reload to update" prompt: each page updates the next time it loads. An old version's cache goes once no open page uses it, checked on activation and on each navigation, and never while a newer worker is still installing.

**Answering requests.** GET requests for the site's own files come from the cache, offline too, whatever their query (`?new`, `?template=`); a folder is its `index.html`, and a folder without its slash (`/quire`) is redirected to it. `updater/` (the update check, the zips), `sw.js`, other methods and anything not in the zip go to the network; a navigation to a page not in the zip that the network can't answer goes to the Start Center.

**Progress.** While it installs, the worker posts `{ type: 'vo-cache', state: 'progress', update, progress, received, total, version }` to every page of the site (progress: the download up to 0.8, then the unpacking; received and total: the zip's bytes, total 0 if the server didn't say), then `{ state: 'failed', error }`, or `{ state: 'done', update }` once the new worker has taken over (from its activation, so a reload is answered by the new version). `common/suite.js` turns these into a `vo-cache` event on `window`. The Start Center shows *Updating cached resources* (*Caching resources for offline use* on the first visit) above the GitHub button, with a progress bar and the megabytes (*1.9 of 4.2 MB*); after an update it turns into a notice with a green tick that draws itself and pulses a few times (none with reduced motion), *Just updated successfully, Click here to reload*; a click reloads the Start Center in the new version (other open pages get it the next time they load).

`node --test tests/sw.test.mjs` checks all of this on staged copies (docs/testing.md).
