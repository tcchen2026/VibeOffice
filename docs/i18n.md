# The UI in other languages

VibeOffice's UI can be shown in Japanese, Korean, French, German, Simplified Chinese and Traditional Chinese as well as English. New documents follow the same choice (paper, fonts, line grid; Defaults below), and the apps draw East Asian fonts (Fonts below). Number and date formats, and Ledger's formula language (decimal commas, `;` between arguments, localized function names), are a later phase.

## Choosing the language

One suite-wide setting, `vibeoffice.lang` (`VO.settings`: the browser's localStorage, the desktop app's `~/.vibeoffice/config.json`): `auto` (the default), `en`, `fr`, `de`, `zh-CN`, `zh-Hant`, `ja`, `ko`, and `qps`, the pseudo-locale for developers. Auto takes the first of the browser's languages (`navigator.languages`) that VibeOffice has, else English. The user changes it in the Start Center's Settings or Tools ▸ Options ▸ General of any app; it applies to the windows opened afterwards.

The shared `common/lang.js`, loaded in every page's head before the stylesheets, resolves it into `<html lang>` (`qps-ploc` for the pseudo-locale) before the first paint, so the chrome's fonts are right from the start; `?lang=xx` in a page's address overrides the setting for that page. The test helpers (`tests/lib/input.mjs` `open`, `tools/ooxml/cdp.mjs` `openPage`, `tools/shot.mjs`) open pages with `lang=en`, whatever the browser's language; `open(app, { lang: 'qps' })` and `node tools/shot.mjs quire/ --qs lang=qps` show another.

Chinese tags are matched before reducing other languages to their base tag: `zh-TW`, `zh-HK`, `zh-MO`, and `zh-Hant` (including subtags such as `zh-Hant-HK`) select `zh-Hant`; bare `zh` and all other `zh-*` tags select `zh-CN`. Matching is case-insensitive. The same rule applies to browser preferences, `?lang=`, and stored choices; pickers and dictionary filenames use only the canonical IDs `zh-CN` and `zh-Hant`.

## `common/i18n.js`

Loaded after `core.js` in each app (after `suite.js` on the Start Center). It reads the page's language and fetches its dictionary, `public/common/i18n/<lang>.json`, a flat JSON object from the English text to its translation; the apps start once it is here (`VO.i18n.whenReady`; at once for English, which fetches nothing).

- `VO.t(s, ...args)`, also `L.t`: the translation of `s`, else `s` itself; `{0}`, `{1}`… are filled from `args`. A translation whose placeholders differ from the English is not used.
- `VO.i18n.lang`: the page's UI language. `VO.lang`: the setting (`list()`, `get()`, `set(id)`) and shared tag resolution (`normalize(tag)`, `resolve(choice, browserLanguages)`), defined by `common/lang.js`. `suite.js` preserves this early namespace.
- `VO.i18n.dates`: the locales argument for dates the chrome shows (Recent Files, Document Recovery): the UI's language, or with English the browser's own. Dates and numbers inside documents are the later phase.
- The pseudo-locale `qps` uses the English catalog as its dictionary: every catalogued string that goes through `VO.t` comes out accented, in brackets and about 40% longer (French and German run longer than English), with placeholders and access keys (`&F`) untouched; other text (a file name) stays as it is. Plain English left in a `qps` screenshot is UI text that doesn't go through `VO.t` or isn't in the catalog yet; a cut-off string is a control too narrow for the longer languages.

## Writing UI text

UI text is English in the code. A string the user sees goes through `L.t`, whole: a sentence with a value in it is one string with a placeholder, `L.t('Do you want to save the changes to {0}?', name)`, never English pieces joined together, which can't be translated (plurals are two strings, `'{0} file'` and `'{0} files'`). Most text needs nothing more, because the helpers translate what they show:

- `L.h` (and the Start Center's `h`): `text`, `title`, `placeholder`, `aria-label`, `data-tip` and string children.
- `common/ui.js`: labels (`stripAmp`, `ampHTML` and everything built on them: menus, toolbar buttons, the ribbon, dialog titles and buttons, `ui.button`, `ui.check`, `ui.radio`, `ui.field`, `ui.group`, `ui.tabs`), the labels of `ui.select`'s `[value, label]` options (plain values, a font or a size, are shown as they are, as are `ui.combo`'s lists and menu rows marked `raw`), `ui.msg`, `ui.toast`, `ui.busy`, tooltips, and shortcut key names (`ui.keyText`: Ctrl, Shift…). `ui.accessKey(label)` is the access key of the label as shown; `ui.plainAmp(label)` the English label without its `&`, for logic.
- The page's own HTML is translated once at start (`VO.i18n.translateTree`).

One English word can need different words in another language: "Line" is a drawn line, but as a chart type it is 折れ線 in Japanese and Courbes in French. Such a string carries its context after a `|`: `'Line|chart'` shows as "Line" in English and has its own entry in the catalog, and until it has a translation of its own it takes the plain "Line"'s. The context is a few lowercase words (`chart`, `number format`, `key`, `mode`); `ui.plainAmp` drops it where the English label is logic. Shortcut key names are `'Home|key'` and so on, apart from a Home button's "Home".

Text set directly (`el.textContent = 'Ready'`) needs `L.t`. Text kept in a table and shown later is marked with `L.N('Turquoise')` (`VO.N` on the Start Center, a local `N` in files that load before `i18n.js`), which returns it unchanged but puts it in the catalog; where it is shown, `L.t` or one of the helpers translates it. Text that is also program logic (a button found by its label, a category compared by name, text written into the user's file) stays English where it is used and is translated only where it is shown; data that isn't UI text (AutoCorrect entries, font names, file names, a slide's title) is marked `translate="no"` on the element that shows it, which `L.h` then leaves as it is (data that happens to match a UI string, a font named Symbol, would otherwise be translated) and the harvest skips.

## The catalog and the tools

`public/common/i18n/en.json` is the English catalog the translations follow: every UI string with where it is written. `node tools/i18n.mjs gather` rewrites it from a scan of the code: a string literal counts when it is an argument of `L.t` / `L.N`, sits where the UI takes text (a label, tip or title property, a `ui.*` label argument, a child of `h()`, the label of a `ui.select` option, an AutoShape or IntelliArt layout name), or reads as an English sentence or label; plus the pages' HTML text and Ledger's function descriptions; in readers, writers and engines (its `SKIP` list) only what is marked with `L.t`, `L.N` or `N`, such as an error message shown to the user. It also lists, in `tmp/i18n/untranslatable.txt`, the English still joined from pieces or put in template literals with values. `node --test tests/i18n.test.mjs` checks that the catalog is current and that the untranslatable count only goes down.

`node tools/i18n.mjs harvest [quire ledger lectern start]` opens each app in the pseudo-locale, then every menu and submenu, task pane, ribbon tab and dialog (the commands whose names end in "…"), and writes `tmp/i18n/harvest-<app>.txt` (English still on screen, outside the document and `translate="no"`), `tmp/i18n/missed-<app>.txt` (text the code asked `L.t` for that the catalog lacks) and `tmp/i18n/cut-<app>-qps.txt` (text its box cuts off or ends with "…": a control too narrow for longer languages; task pane titles and template names are shortened on purpose). For the translator, `harvest --lang de` lists only what is cut off in that language. `node tools/i18n.mjs status` counts, for each language, the translated, missing and obsolete entries and the placeholders that differ, and writes `tmp/i18n/<lang>-todo.json`, the missing English for the translator. For the translator, `node tools/i18n.mjs chunks <lang>` splits the missing English into pieces in the order of the code (`tmp/i18n/<lang>/todo-NN.json`, each string with where it is written), and `node tools/i18n.mjs merge <lang> <files>` adds translated pieces (`{ "<English>": "<translation>" }`) to the language's file, leaving out and listing (`tmp/i18n/<lang>-problems.txt`) an entry whose placeholders or access key mark differ from the English.

## Translations

Translating is a task of its own, done only when the user asks for it (AGENTS.md); in other work agents don't read, write or check the translation files. All six non-English languages are translated in full (18 October 2026, 6,053 catalog entries), in the terms of each language's Office 2003 (Office 2016's for ribbon-only items); new English shows untranslated until the next round: `status` lists what is missing, `chunks` and `merge` take it through, `prune` drops what the catalog no longer has, and `harvest --lang xx` shows what a language cuts off. Font family names keep their installed names in every language. About descriptions stay general in English and every translation, without naming another company's products. The translator works on `public/common/i18n/<lang>.json`, one entry per English string:

- `&` marks the access key, as in the English (`&File`); for Japanese, Korean and Chinese, Office's style puts the English letter after the text, `ファイル(&F)`. `&&` is a literal `&`.
- `{0}`, `{1}`… stand for values filled in when the text is shown, and must all appear in the translation.
- `Line|chart` is "Line" in the context after the `|`: the translation is of "Line" as that (折れ線), without the context. Where a plain string still covers two meanings in a language, the code gets a context for one of them.
- Text that becomes part of the user's files (sheet and object names, placeholder prompts written into a presentation) stays English this round and is not in the catalog.
- Ledger's function descriptions are adapted from Microsoft's documentation (CC BY 4.0); a translation keeps the credit.

The two Chinese catalogs are authored and reviewed together. Simplified Chinese uses terms such as 文件, 工作簿, 单元格 and 幻灯片; Traditional Chinese uses 檔案, 活頁簿, 儲存格 and 投影片, with spreadsheet rows as 列 and columns as 欄. Formula names, format codes and placeholders stay intact. Both use English-letter access keys, such as `文件(&F)` / `檔案(&F)`.

## Defaults for new documents

A new document, workbook or presentation takes the defaults of the UI's language, as the Office of that language makes its blank files (`public/common/locales.js`, `L.locale.get()`):

- Quire (`D.applyLocale`, for the documents the user starts: File ▸ New, a blank window, the start-up document): Japanese and Korean pages are A4 with Office's margins and their Normal style justified without widow control; Japanese text is 10.5pt Century with ＭＳ 明朝 on an 18pt line grid, with punctuation compressed (`characterSpacingControl`) and the theme's Japanese font, and the styles English Word gives Arial or Tahoma (headings, Title, Subtitle, Balloon Text…) have the theme's heading font, ＭＳ ゴシック, beside it (Korean and Chinese themes use the text's East Asian font for headings too, so their styles keep it); French and German pages are A4 with 2.5 cm margins (German: 2 cm at the bottom) and their language set for the text. Simplified Chinese uses Times New Roman with 宋体 10.5pt on a 15.6pt line grid; Traditional Chinese uses Times New Roman with 新細明體 12pt on an 18pt grid, its text tagged `zh-HK` in all three apps (Word ignores `zh-Hant`, a tag without a region). Both use A4, 2.54 cm top/bottom and 3.175 cm left/right margins, compressed punctuation and no widow control; Simplified Chinese is justified. Rulers and measurements are in centimetres in all six.
- Ledger (`A.blankWorkbook`): A4, and Japanese and Korean workbooks have their Excel's default font (ＭＳ Ｐゴシック 11, 맑은 고딕 11) with its row height. Chinese uses 宋体 11 (13.5pt rows, charset 134) or 新細明體 11 (14.25pt rows, charset 136).
- Lectern (`M.newPresentation`, not for a file being read): the text's language (`lang`, also for new text in an opened presentation, from its default text style) and, for Japanese, Korean and Chinese, the theme's East Asian font (Chinese: 宋体 / 新細明體).

AutoCorrect's quotes follow the language of the paragraph being typed, as Word's do: « » (with no-break spaces) in French, „ “ in German (`L.locale.quotes`).

The values were read from the corpora's Office-saved files with `python3 tools/locale-defaults.py` (the counts are in the table's comments); Korean's fonts are Office's known ones, not yet seen in a Korean Office's file. Only new documents get them, never a file that is opened, and the user's own settings come first: Page Setup's Default…, Ledger's standard font, Quire's measurement unit. Those options are saved only when the user chooses another value than the language's (`L.locale.optsToSave`), so they keep following the language otherwise; in options saved before there were languages, a value equal to English's default is taken as not chosen. `node --test tests/locales.test.mjs` saves a blank file of each app in Japanese, Korean, Chinese, French, German and English and checks what they hold.

## Fonts

`common/core.js` knows the East Asian fonts Office uses, by their English names and the names Japanese, Korean and Chinese Office write (ＭＳ 明朝 is MS Mincho, 맑은 고딕 is Malgun Gothic): `L.fontKey(name)` is the key every font table uses, `L.fontIsEA(name)` tells them apart, `L.hasEAText(text)` finds the characters an East Asian font draws, and `L.fontStack(latin, ea)` gives a run's CSS fonts, its letters from the first font and its East Asian characters from the second, with the fonts a Mac, Windows or Linux computer has in their place (none is vendored: several megabytes each). With a Japanese, Korean or Chinese UI the Font boxes list that Office's fonts too.

- Quire draws a run with its Latin and East Asian fonts (`w:eastAsia`, or the theme's: its `a:ea`, else its font for the script of `themeFontLang`'s East Asian language), and text with East Asian characters in the run's East Asian language (`lang`), so the browser picks Japanese, Korean or Chinese glyphs. Where East Asian text is typed, the Font box and the status bar show the run's East Asian font and language, as Word does with an East Asian keyboard (`A.typingEA`): the selection has East Asian characters, or the character before the insertion point is one; with no text there, a Japanese, Korean or Chinese UI stands in for the keyboard, which the page can't see. So a new Japanese document shows ＭＳ 明朝 and 日本語, and after `abc` Century and English (U.S.). As in Word, an East Asian font chosen in the Font box is for all the text (`w:ascii`, `w:hAnsi` and `w:eastAsia`), a Western one for the Latin text only. Each font's single line height (`R.lineFactor`; for East Asian text the larger of its two fonts') decides how many grid pitches a line takes. The East Asian fonts' factors come from their Windows metrics and are unverified: `python3 tools/linegrid.py fonts` writes a document to measure them from Word's PDF (`read-fonts`).
- Lectern reads a run's East Asian font (`a:ea`; `+mn-ea` and `+mj-ea` are the theme's, as in Quire) and draws it the same way. Changing a run's font writes `a:latin` and `a:cs` and keeps its `a:ea`.
- Ledger keeps a Japanese, Korean or Chinese workbook's own font where the style names an East Asian font with a theme (ＭＳ Ｐゴシック, not the theme's Latin Calibri), and knows its digit width and row height.

With a Simplified Chinese UI the Font boxes also list the common open-source Chinese families, under the names they are installed by. None is bundled; a document keeps the name the user picks, as with any font.

| In the list | Family | Names from |
|---|---|---|
| 文泉驿微米黑 | WenQuanYi Micro Hei | [WenQuanYi Micro Hei](https://sourceforge.net/projects/wqy/files/wqy-microhei/) |
| 思源黑体 | Source Han Sans SC | [Adobe's family-name table](https://github.com/adobe-fonts/source-han-sans/blob/release/SourceHanSansReadMe.pdf) |
| 思源宋体 | Source Han Serif SC | [Adobe's family-name table](https://github.com/adobe-fonts/source-han-serif/blob/release/SourceHanSerifReadMe.pdf) |
| Noto Sans CJK SC, Noto Serif CJK SC | Same as listed | [Noto CJK](https://github.com/notofonts/noto-cjk) |
| Noto Sans SC, Noto Serif SC | Same as listed | [Noto's language variants](https://github.com/notofonts/noto-docs/blob/main/docs/website/use.md#which-noto-fonts-should-i-use-for-chinese-japanese-or-korean) |

Adobe's Chinese names for the SC families have no `SC` (思源黑体, 思源宋体), and its `CN` subsets and `VF` variable fonts are other families; Noto's `SC` and `CJK SC` fonts are separate installed families, so both are listed. Source Han and Noto CJK are the same designs ([Noto's explanation](https://github.com/notofonts/noto-docs/blob/main/docs/website/use.md#is-noto-based-on-existing-fonts)), so each stands in for the other before the computer's own Chinese fonts; WenQuanYi Micro Hei falls back as Microsoft YaHei does, and the Office fonts fall back to Source Han after Noto.

The chrome uses local Microsoft YaHei/PingFang SC/Noto SC fallbacks for `zh-CN`, and Microsoft JhengHei/PingFang TC/Noto TC for `zh-Hant`, in `looks.css`; no fonts are downloaded from other servers.

`node --test tests/fonts.test.mjs` checks the names, the stacks and Ledger's rows.

## Adding a language

A language normally uses the first part of the browser's tag (`es`); variants such as `zh-CN` and `zh-Hant` have explicit normalization rules. Add it in these places:

1. `public/common/lang.js`: `LANGS` (its name in itself, for the language pickers) and any variant handling in `normalize`. The UI and all four pages share this resolver.
2. Every page already loads `common/lang.js` before the stylesheets; there are no per-page language lists to edit. A newly added page needs this script too. Ledger's page is generated from `tools/ledger/build/template.html` with `python3 tools/ledger/build/make.py`.
3. `tools/i18n.mjs`: `LANGS`, so `status`, `chunks`, `merge` and `prune` take it.
4. `public/common/i18n/<lang>.json`, started as `{}`: the UI shows English until it is translated, which is a task of its own (Translations above).
5. `public/common/locales.js`: its entry in `LOCALES` (`{}` keeps the apps' English defaults), and in `QUOTES` if its quotes aren't “ ” ‘ ’. The values come from Office-saved files in the corpora: add the language to `tools/locale-defaults.py` (`LANGS`, and how it tells a file of that language's Office), put the counts in the table's comment, as for the others, and add a case to `tests/locales.test.mjs`.
6. For an East Asian language: its UI fonts in `public/common/looks.css` (`:root:lang(xx) { --ui-cjk: … }`), its Office's fonts in `L.FONT_LIST` (`public/common/core.js`, shown with that UI), and those fonts in the tables of Fonts above (`L.fontKey`'s names, the fallbacks, Quire's line factors, Ledger's digit widths and row heights). Chinese fonts are there already, and so is Chinese in the theme's script fonts (`Hans`, `Hant` beside `Jpan` and `Hang` in Quire's and Lectern's readers and writers), Lectern's `altLang` (`pptx-write.js`) and search's matching of text without spaces (`CJK` in `public/common/search.js`); a script outside these (Thai) needs its range added there.
7. The docs that name the languages: the start of this file, Choosing the language, docs/suite.md (Language) and AGENTS.md; and the Start Center (`public/index.html`), which lists them for search engines: `inLanguage` in its JSON-LD, its name in the welcome's line of languages and the feature list (`tests/seo.test.mjs`).

Then check `?lang=xx` in each app and the Start Center, run `node --test tests/i18n.test.mjs tests/chinese-language.test.mjs tests/locales.test.mjs`, and once it is translated, `node tools/i18n.mjs harvest --lang xx`.

Not handled yet: a right-to-left language (Arabic, Hebrew) needs `dir="rtl"` on the chrome.
